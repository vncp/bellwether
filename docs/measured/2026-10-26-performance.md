# Measured: release performance (WP22a)

Measured on 2026-10-26 (UTC) by [`scripts/perf.sh`](../../scripts/perf.sh) on one machine, with one release binary. Each section's start, commit and load are in [How it ran](#how-it-ran). The numbers and every raw sample are in [`2026-10-26-perf.json`](2026-10-26-perf.json) (`bellwether-perf/1`, [definitions](../benchmark.md#2026-10-25-release-measurements-and-the-perf-schema-wp22a)). The tables below are printed from that file by [`scripts/perf-report.py`](../../scripts/perf-report.py); none was typed by hand. The README charts come from the subset in [`results/perf.json`](results/perf.json). The budgets derived from this run are in [`budgets.toml`](budgets.toml).

- **Machine.** Apple M3 Pro, 12 cores, 36 GiB, macOS 26.4.1, local SSD.
- **Build.** Release: thin LTO, codegen-units 1, line-table debug info so the profiles have names; rustc 1.99.1. One binary, built once from `f809e54` and not rebuilt: cargo reported nothing to do at the start of every run. The Rust sources are identical at every commit named below (`git diff f809e54 ff52312 -- crates` changes only the bench README); later commits changed only the scripts and docs.
- **DuckDB.** v2.0.0 (d54cbbe3df), the CLI, on the same files.
- **Cache.** Warm means the same call ran just before. Cold means a new process, with bellwether's cache directory removed before each sample. The OS page cache could not be dropped (that needs root), so cold here is **process-cold**: file reads still came from memory. Cold-cache disk reads are not measured on this page.
- **Data.** Two corpora are generated by seeded scripts in this repository: `bellwether bench market` (the defaults, and a 10x one: 3,000 symbols, 30 days) and the synthetic ledger's small rung (`bellwether bench generate --rung small`). Two are public: the GH Archive hours 2024-01-01 00 to 11 and the NYC yellow-taxi months 2024-01 to 2024-06, both as [`scripts/realdata.sh`](../../scripts/realdata.sh) prepares them ([the real-data page](2026-10-24-realdata.md) describes them). No production data, and no production numbers.

## Measured under load

The machine was shared, and no section ran on a fully quiet one. Other agents had stopped their work for the timing slots. The owner's desktop apps and a separate build in another repository kept running:

- **lookups**: processes outside the run used up to 10.7 cores at the peak (a `rustc` at 812%);
- **build, reconcile, profiles**: 3.3 to 7.5 cores at the peak;
- **latency**: 1.9 cores at most.

Every timing in the lookups, build and reconcile sections is therefore **measured under load**. Treat it as an upper bound for this machine. Counts are not affected: row groups, bytes, passes, segments, meter peaks and resident bytes per key do not depend on load.

A rerun of lookups, build, latency and profiles on a quiet machine will replace those rows (`perf.py --merge`). This page will then say which rows it superseded.

"(dirty)" in the table below has one cause only: the run had already rewritten `docs/measured/results/perf.json`, which `perf.py` itself writes. No source file was modified. `perf.py` now leaves that file out of the check.

## Findings

1. **The reconcile memory bound is exceeded at small budgets.** On the ledger small rung, 8,000,000 rows a side, with `latest_by` and totals by group, the process's peak memory grows as the budget shrinks:

   | budget | passes | meter peak | peak RSS |
   |---|---:|---:|---:|
   | 1 GiB | 1 | 164.4 MiB | 469 MiB |
   | 256 MiB | 3 | 68.4 MiB | 1,127 MiB |
   | 64 MiB | 10 | 18.3 MiB | 1,630 MiB |

   The verify README states the bound: the budget, plus one decoded row group (`peak_batch_bytes`: 39.7 MB here), plus fingerprint lists, plus a footer cache capped at 256 MiB. At 64 MiB that is about 360 MiB, and the measured peak is 4.5 times that.

   This is dirty memory, not mapped file pages. A separate `/usr/bin/time -l` run of the same command reported a peak memory footprint of 1,708,165,280 bytes. The repro, from `PERF_WORK`:

   ```sh
   bellwether reconcile ledger-small/data ledger-small/data-copy --key entity_id --latest-by version_ts \
     --totals amount --group-by status --memory-budget 64M --index /tmp/rss-idx --quiet
   ```

   The taxi pair at 64 MiB (224 passes) stays at 460 MiB, so the extra memory does not simply grow with the number of passes. The cause is open and needs a heap profile. It is reported as a defect, separately from this page.
2. **Planning, not reading, is where a lookup's time goes, and it scales with the number of keys.** On `market-10x` (2,268 row groups), with `locate --window` over 1 day, the warm p50 plan takes:

   - 86 ms at 10 keys;
   - 615 ms at 300 keys;
   - 5.4 s at 3,000 keys.

   Reading the planned row groups then adds 1 to 22 ms. DuckDB answers the same queries over the same files in 16 to 61 ms, and a full scan through the byte-counting reader takes 36 ms. On these corpora, on a local SSD with the page cache warm, the plan is never faster end to end than a full scan or DuckDB.

   The bytes it avoids are real: 241 KB planned of 31.9 MB at 10 keys. They save no wall time here, because this measurement has no slow storage. The profile says why the plan is slow: see hypothesis 1.
3. **Build throughput scales with threads on `market-10x` (2.65x at 12 threads) but barely on the ledger rung (1.38x).** On the ledger rung, 80 row groups become 14 segments, for 2 specs.
4. **One reconcile pass needs much more budget than one pass's state.**

   - **Ledger rung.** One pass needs 592 MiB of budget for 164 MiB of state (3.6x). It holds 401,325 keys over 8,000,000 rows.
   - **Taxi.** One pass needs 16 GiB for 9.9 GiB of state (1.65x). It holds 20,314,139 keys over 20,332,093 rows.

   Below those budgets, the pass count is higher than the state requires.
5. **The observe tier and replay are within their budgets by a wide margin.**

   - `why` with no workload answers in 16 to 23 ms at p50 (100 ms budget): through the facade, through MCP in process and over stdio, and through the CLI including process start.
   - The replay p50 run is at most 0.47 ms (5 ms SLO).
6. **Resident bytes per key (contract v3 entry 32)** were measured in a release build.

   - **An open transient segment writer** holds **320 bytes per key** resident, against 9 bytes accounted (35.6x).
   - **The layout map** holds **84 bytes per key**, against 73 accounted (1.16x).

   The replay README now states both constants.

## Lookups

The columns:

- **plan**: one `bellwether locate|latest|asof … --json` process. That is process start (6.4 ms at p50 for `bellwether --version`), opening the manifest, reading the key file, planning, and recording the Evidence.
- **plan + read**: the plan, then `bellwether bench read --plan`, which reads every column of every planned row group through the benchmark's byte-counting reader.
- **full scan**: the same reader over every row group.
- **DuckDB**: the same lookup as SQL over the same files, hashing every column of every matched row; this is DuckDB's own `.timer`, without process start.

Warm is 20 samples; cold is 5, process-cold (see above). Key sets are 10, 300 and 3,000 distinct keys, chosen by a seeded hash. `market-default` has only 50 symbols, so it has the 10-key set only.

The lookups:

- `locate-window-1d|30d`: `locate --window` over 1 or 30 days ending at the corpus's middle hour.
- `latest`.
- `asof`: `asof --at` that hour.
- `asof-lookback-1d|30d`: `asof --lookback`.

Every planned row group and byte count is exact and comes from the plan's `--json`.

## Build throughput

`bellwether index --threads N` into a fresh index, the median of 3 runs. Throughput is the row groups read divided by the wall time. Peak RSS is from `/usr/bin/time`. "Per worker" is that peak minus the peak of the same command over an already complete index, divided by `N`; "all" is 12. The segments written do not depend on `--threads`, and `tests/perf.rs` checks that the segment files are byte-identical. The first commit over a v1 index (the footer pass) is not measured: it needs WP14, and 22b measures it.

## Reconcile

Full coverage, with `latest_by` and totals by group, at budgets of 8 GiB, 1 GiB, 256 MiB and 64 MiB, largest first. Throughput is one side's rows divided by the wall time. The meter peak is the accounted comparison state (`outcome.memory.peak_state_bytes`); peak RSS is the whole process.

The smallest one-pass budget is found by bisection to 10%, starting from the one-pass run's state. When no listed budget gives one pass, the search doubles past the largest one first, up to half the machine's memory.

The two pairs:

- **Ledger rung**: `--key entity_id --latest-by version_ts --totals amount --group-by status`, the rung against a byte-for-byte copy.
- **Taxi**: `--key VendorID,tpep_pickup_datetime,PULocationID,fare_amount --latest-by tpep_dropoff_datetime --totals fare_amount:dec(2) --group-by VendorID`, the six months against DuckDB's rewrite of them.

Both pairs pass. For one pass, the ledger rung's 401,325 keys need 592 MiB, **640 MiB** in round figures, and taxi's 20,314,139 keys need **16 GiB**. The verify README cites both.

## Budgets

[`budgets.toml`](budgets.toml) is written by `scripts/perf-budgets.py` from this run's `perf.json`. For every latency it holds measured × 1.25, and for every throughput measured ÷ 1.25. Each entry carries the section's start time and commit; the machine and build are at the top of the file.

Context metrics have no budget: counts, passes, meter peaks, bytes planned, and the smallest one-pass budget. The `[runner]` section is empty until WP22b's first `perf.yml` run measures the CI runner's own baseline. Nothing asserts a budget yet.

Budgets taken from the sections measured under load are loose by however much that load slowed them. The quiet rerun replaces them in the same pull request that lands it.

## Not measured here

- **Cold-cache disk reads.** The OS page cache could not be dropped without root.
- **The DataFusion baseline.** It comes from the nightly runner; the `datafusion` feature is never built locally.
- **The footer pass of a first commit over a v1 index.** It needs WP14.
- **A profile of the ledger rung's build** (hypothesis 7).
