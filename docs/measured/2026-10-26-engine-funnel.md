# Measured: the engine loop on both bench shapes (WP20b, ADR 033)

Measured on 2026-10-26 (UTC) with [`scripts/engine-funnel.sh`](../../scripts/engine-funnel.sh): each shape is loaded into ClickHouse, diagnosed on its lake twin, rewritten, and scored, verified, and attested by `fix`. The script was run twice, and both runs gave the same rows and bytes.

- **Machine.** Apple M3 Pro, 12 cores, 36 GiB, macOS 26.4.1, local SSD.
- **Build.** A `bellwether` **debug** build of the sources at `16ecca2` (branch `a-engine`), rustc 1.99.1.
- **Engine.** ClickHouse 26.11.1.782, a local server on the same machine (HTTP on port 18123, user `default`, no password).
- **Load.** The machine was shared with other builds. The 1-minute load average was 10.2 at the first run and 8.4 at the second.
- **Data.** Generated by `bellwether bench` in the script; no download and no production data.
  - **Ledger:** `bench generate --seed 7 --days 8 --files 32 --row-groups-per-file 4 --rows-per-row-group 2000 --entities 20000 --churn 0.1`: 256,000 rows in 32 files and 128 row groups.
  - **Time series:** `bench market --rung small`: 102,739 trade prints in 20 files over 10 days.
- **Command.**

  ```sh
  CH=http://127.0.0.1:18123/ BW=$CARGO_TARGET_DIR/debug/bellwether scripts/engine-funnel.sh /tmp/a-funnel
  ```

## Which numbers are claims

- **Exact.** These are the same on every run of the same query against the same parts:
  - rows and bytes the engine read, from `system.query_log`;
  - result rows;
  - the twin's prediction and every lake count.
- **Not claims.** Peak memory, CPU time, and duration are single samples taken on a loaded machine. Both runs are shown so the spread is visible. `fix` never treats them as a gain: the gain gate counts bytes read only.
- **Tables.** Both ClickHouse tables are sorted by the lookup key (`ORDER BY (entity_id, version_ts)` and `ORDER BY (symbol, ts)`). They use small granules (`index_granularity = 1024`) so the engine's pruning shows on a corpus this small.

## The rewrite: dedup before filter

Both shapes ask the same question: the newest row of each key in a key set.

- **Before.** The query numbers the rows of every key newest-first over the whole table (`row_number() OVER (PARTITION BY key ORDER BY ... DESC)`), and only then keeps `rn = 1` for the wanted keys.
- **After.** The query filters on the key inside the subquery, so the engine's primary index skips the granules no key touches.
- **Why a window function.** ClickHouse pushes a filter down through `LIMIT 1 BY` by itself. The script's first draft used that form and measured no gain (the same 16,412 rows and 2,681,613 bytes on both sides), and the gate refused it with `nothing_to_gain`. ClickHouse does not push a filter down through a window function.

The key sets come from the engine itself: `workload record --from-engine --keys-query`.
- **Ledger:** `SELECT DISTINCT entity_id ... WHERE entity_id BETWEEN 7000 AND 7099`, which returns 59 keys.
- **Market:** `SELECT DISTINCT symbol ... WHERE symbol IN ('S0003', 'S0017', 'S0029')`, which returns 3 keys.

What these numbers mean:
- **Ledger.** The rewrite reads 15.8× fewer bytes and 15.6× fewer rows.
- **Market.** The rewrite reads 3.0× fewer bytes and 2.9× fewer rows.
- **Certificates.** Both passed: full coverage, 0 mismatched, 0 missing on either side.
- **Receipts.** Both receipts are attest-only: the manifest stayed at sequence 0, and the receipt carries the replay's prediction.
- **Exports.** They were deleted after the certificate: 19.2 kB (ledger) and 4.7 kB (market).
- **Engine identity.** It was unchanged through the exports in every run.

## What it says about the twin

- **The ratio is per table.** It differs by shape.
  - On the market table, sorted by symbol, the engine read 5.7× the rows the twin predicted for the key set.
  - On the ledger table, it read 11.8×.
  - Both are well above 1, because a ClickHouse granule (1,024 rows here) is coarser than a key's rows. Over receipts, this ratio says how far `why` on the twin can be trusted for a table before the engine must be measured.
- **Lints.** `dedup_before_filter` did not fire on either shape, though the rewrite is that pattern.
  - On the ledger, the key sample selects 30 of 32 files, far above the lint's 1% threshold.
  - On the market corpus, it selects all 20 files.
  - The lint asks for a key sample that selects under 1% of files, and these corpora are too small for that.
  - This is one case toward ADR 033's kill criterion: five receipts across two engines.
