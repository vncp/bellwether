# Measured: taxi trips and GitHub events through every CLI verb

Measured on 2026-10-24 by running [`scripts/realdata.sh`](../../scripts/realdata.sh) once against the CLI at commit `3b6078b` (main). Nobody on this project generated the data. Every `bellwether` call was run by the script, which recorded its output, exit code, and wall time. The full transcript is at the end of this page, verbatim.

- **The run.** The downloads under `dl/` were already in place from an earlier pass. The script verified each one against its `Content-Length` and did not fetch it again. Everything after downloading and preparing the data ran from 20:49:49Z to 21:03:08Z.
- **Oracle scope.** The DuckDB oracle was run on both GH exact plans and on all six temporal plans. The taxi `locate` plan was checked against `why`'s prediction only. Every taxi row group holds every key, so there the plan is trivially all 22 row groups.
- **Machine.** Apple M3 Pro, 12 cores, 36 GB, macOS 26.4.1, local SSD.
- **Build.** **Release** (`cargo build --release -p bellwether-cli`), rustc 1.99.1. Wall times depend on the build and on the machine. Bytes, row groups, and counts do not.
- **Tools.** DuckDB v2.0.0, used to flatten the input, sample keys, copy and mutate files, and act as the oracle.
- **NYC taxi data.** Yellow trips for 2024-01 through 2024-06, the files as published at `d37ci6vzurychx.cloudfront.net/trip-data/`. That is 6 files, 22 row groups, 20,332,093 rows, and 341,861,576 compressed bytes.
- **GH Archive data.** The hours `2024-01-01-0` through `2024-01-01-11`, 12 of the 24 hours in the day. Using 12 keeps total downloads at about 1.2 GB, under the 2 GB cap.
  - **Flattened.** The events are nested JSON (`repo.id`, `actor.id`). Section 0 shows that the engine can profile nested files but cannot index them, and cannot address a nested field.
  - **The dataset used here** is therefore DuckDB's flattening of each hour into one Parquet file with the columns `repo_id`, `actor_id`, `type`, and `created_at` (timestamp with time zone, UTC), written with DuckDB's default settings. That is 12 files, 24 row groups, 1,768,515 rows, and 12,817,897 bytes.
- **Key files.** Distinct values were picked by a seeded hash (`ORDER BY hash(col, 42) LIMIT n`).
  - **GH.** 1,000 values each of `repo_id` and `actor_id`, plus 10 values of `repo_id`.
  - **Taxi.** A 1,000-value key file is not possible: `PULocationID` has 262 distinct values and `VendorID` has 3. Each taxi key file therefore holds every value of its column.
- **The 10-key file is an addition to the brief.** With 1,000 keys, every GH row group holds at least one key, so no index can help. The 10-key file shows the same engine in the case where an index does help. The data was not re-sorted or rewritten to manufacture a win.
- **How the transcript was produced.**
  - **Read-only verbs, plus `why`, `index`, `reconcile`, `receipt`, and `report`,** run twice: once for the human output, then again with `--json`. The second call is a real second call. `why` writes new records with new hashes, `index` finds nothing to commit, and a warm profile cache answers in milliseconds.
  - **`propose` and `fix`** change state, so they run once, with `--json`.
  - **Hashes used downstream** always come from the `--json` runs. That is why an evidence hash cited by `propose` differs from the one printed in the human `why` just above it.

### What the checks found

The script printed 14 `CHECK` lines, and every one passed. They cover the following:

- **Prediction against plan.** `why`'s predicted bytes equal `locate`'s planned bytes in four places: taxi, GH with 1,000 keys, GH with 10 keys, and `locate` again after `fix` applied the key.
- **Exact index against the rows.** For both GH key files, `locate`'s row groups and bytes equal an oracle that reads the rows with DuckDB, maps each row to its row group, and sums `total_compressed_size` from the footers.
- **Temporal plans against the rows.** For all six `latest` and `asof` plans, every row group that holds a wanted version is in the plan. Each of these plans in fact equals the oracle's set.

The reconcile verdicts were checked independently in two ways:

- **The planted mutation.** The mismatch the certificate names, `["2","2024-03-01T00:14:03Z","142","7.9"]`, is the row the script changed.
- **The decimal totals.** In the labeled decimal workaround (January only), the exact totals per vendor equal DuckDB's sums: 12,872,146.54, 40,997,884.39, and 12,193.83.

### Where the index helps, and where it cannot

- **Taxi trips, point lookups.** This is the honest negative case, and the bytes say so exactly. Pickup zone and vendor are low-cardinality columns, and every value appears in every row group, because the files are written in time order. Even an exact index on `PULocationID` (the floor) reads 100% of the bytes, so `why` correctly recommends nothing. What it does not do is say *why* in words. See defects 7 and 8.
- **Taxi trips, temporal questions.** The same index answers "the newest trip per zone" from 6 of 22 row groups, and the planner's set is exactly the set of row groups that hold a newest row. `why` cannot see this, because a key file is replayed only as a point lookup (defect 9).
- **GitHub events, 1,000 repositories.** Together these touch every row group, because the events are hour-ordered and not clustered by repository.
- **GitHub events, 10 repositories.** These touch 8 of 24 row groups. Here the tool did the whole loop correctly: diagnose, recommend, predict exactly, verify, apply, attest, and plan the predicted bytes afterwards.

## Defects

Numbered in order of severity. Each entry gives the exact command and output (from the transcript unless marked as a probe) and a reading of the cause. No engine code was changed. The one workaround is labeled in the transcript.

1. **`index` refuses any dataset that has a nested column, even when the key is a flat column.** It fails the same way for JSON lines and for Parquet.
   - **Command and output:** `bellwether index ghnested --key exact:id` printed `bellwether: manifest column "actor" has data type "Struct([Field { name: \"id\", data_type: Int64, ... }])", which this Arrow build cannot parse: Parser error: Unsupported type 'Struct(...)'. Must be a supported arrow type name such as 'Int32' or 'Timestamp(Nanosecond, None)'. Error unrecognized word: Struct` and exited with code 4. `index ghjson --format jsonl --key exact:id` gave the same result.
   - **Reading:** the manifest records every column's Arrow type as a string and parses it back. Nested types do not round-trip, so building is refused before it begins. `why` on the same folders succeeds and records Evidence, so profiling and indexing disagree about which datasets they accept.
   - **Consequence:** raw GH Archive, and any lake with a struct or list column anywhere in its schema, cannot be indexed at all.
2. **Nested fields cannot be addressed, and the errors print Rust `Debug` output.**
   - **Command and output:** `why ghjson --format jsonl --columns repo.id` printed `column "repo.id" not in the dataset schema` and exited with code 4, after profiling for 0.9 s.
   - **A probe showed:** a key file whose `repo` column is a struct printed `type Struct([Field { name: "id", data_type: Int64, nullable: true, dict_id: 0, dict_is_ordered: false, metadata: {} }, ...]) has no canonical encoding in encoding version 1`.
   - **Reading:** canonical encoding v1 has no nested types, and the source layer does not flatten nested fields. The `Debug` formatting of Arrow `Field` reaches the user unchanged.
3. **`reconcile`'s human output does not name the mismatched key.** The brief requires that the failure name the key.
   - **What the human output shows:** `reconcile taxi taxi_duck_mut ...` printed only counts (`mismatched 1`) and the certificate hash, and exited with code 1.
   - **Where the key is:** the `--json` line holds `{"kind":"row_hash_differs","key":{"values":["2","2024-03-01T00:14:03Z","142","7.9"]}}`, which is exactly right.
   - **Reading:** `reconcile_human` in `crates/bellwether-cli/src/verify_cmds.rs` prints `counts` and never prints `mismatches`.
4. **`fix` applies and attests a key that its own replay predicts saves nothing.**
   - **The sequence:** on `ghfix1000`, `why` said `recommended: none; no candidate reads fewer bytes than the current configuration`. Then `propose --key exact:repo_id` followed by `fix` returned `outcome applied, score current 12817897 bytes, proposed 12817897 bytes`, and receipt `f4f9dca8…` was written with every link present.
   - **Reading:** the score stage records the replay but does not gate on it. Only the certificate gates the apply.
   - **Consequence:** the receipt is honest about the bytes, but it attests a change worth zero. A CI gate that checks only "a receipt exists" would wave it through. Possible remedies are a typed refusal (`no_improvement`) or at least a warning.
5. **Reconcile reads a 20-million-row dataset 37 times, and nothing says so.**
   - **What the JSON shows:** both full reconciles report `"passes":37` and `rows_read [752287441, 752287441]` against a fixed `budget_bytes` of 268,435,456. That is 37 passes over 20,332,093 rows on each side, 181 to 186 s per run in a release build.
   - **What the human output and CLI lack:** the human output does not mention the passes, and the CLI has no flag to raise the budget.
   - **Reading:** this is the documented bounded-memory design. A 256 MiB state budget is small for 20 M keys, and the cost appears as wall time with no explanation.
6. **A `--totals` refusal is labeled as a key spec error, with the engine-error exit code.**
   - **Command and output:** `reconcile taxi taxi_duck --key ... --totals fare_amount` printed `bellwether: key spec error: invalid reconcile spec: total column "fare_amount" is Float64, not a decimal; totals are exact decimal sums and never use floats` and exited with code **4**.
   - **Reading:** the message is clear and the refusal is by design (totals are exact decimals). However, the request is a usage error, which is exit 2, and the prefix "key spec error" is wrong.
   - **A gap rather than a bug:** a passing `--totals` run prints only `totals that differ 0`, never the totals themselves. They appear in the JSON only.
7. **`why`'s culprit line blames a missing index where no index could help.**
   - **The output:** on taxi, `culprit (PULocationID): no index serves this lookup, so it reads every row group`. The floor two lines above reads every row group too.
   - **Reading:** the culprit is chosen as `no_index_serves` whenever no current spec serves the workload, without checking whether the floor equals the current cost.
   - **Contrast with the README:** the README's ClickBench page says in prose that layout, not a missing index, is what the job pays for. The tool itself never says this.
8. **No lint and no verdict on the taxi profile.**
   - **The output:** `why taxi` with no keys prints a fanout table in which every candidate touches 20 to 22 of the 22 row groups, and then nothing else: no lint and no summary line.
   - **Reading:** `low_selectivity_single_column` requires a composite partner that halves the fanout. On taxi, no composite does (`PULocationID, DOLocationID` still has a p95 of 22), so the rule correctly stays silent. But no rule says "no column in this dataset prunes, and the layout is time-ordered".
   - **Note on the brief:** the brief's "`why` should say an index helps little, and say why" is met by the numbers and not by the words.
9. **`why` replays a key file only as a point lookup.**
   - **The gap:** on taxi, `why --from keys/taxi_pu.parquet` recommends nothing. Yet `latest` with the same keys and the index plans 6 of 22 row groups (94.4 MB instead of 341.9 MB), and `asof` plans 8 of 22.
   - **Reading:** a key file becomes a one-run workload of exact lookups, and there is no way to tell `why` that the run asks for the newest version, so the temporal saving is invisible to it.
10. **A lint says there is no recorded workload while a workload is on screen.**
    - **The output:** the GH `why --from keys/gh_repo.parquet` output shows `funnel: 1 run(s)` and then a lint ending `(no recorded workload: this order assumes lookups supply repo_id)`.
    - **Reading:** this is documented. A key file has no route into the profile's supplied columns, only a bench workload does. Still, the human output contradicts itself. The lint could say "a key file does not inform the profile" instead.
11. **JSON lines files are discovered by extension only, and the error does not say so.**
    - **Command and output:** `why ghjson --format jsonl` on a folder holding `2024-01-01-0.json` printed `source error: .../ghjson: no JsonLines files` and exited with code 4. Renaming the file to `.jsonl` made it work.
    - **Reading:** discovery matches `jsonl` and `ndjson` only, and the message does not list the accepted extensions. `.json` is the most common name for this format, and it is the name GH Archive uses.
12. **Cosmetic: the `index` table misaligns long spec labels.** The output line is `temporal:PULocationID@tpep_pickup_datetime              1`, where the "complete at" column shifts right because the label is wider than its fixed column.
13. **Record timestamps use mixed precision.** In `receipt show`, the certificate's `created_at` is `2026-10-24T21:03:02.927473000Z` (nanoseconds), while every other record uses milliseconds (`21:03:02.069Z`). Two writers format the clock differently.
14. **`docs/agent-loop.md` is out of date.** It still says "The types exist; the engine that writes them does not yet." The engine now writes every record this page shows.

Not defects, recorded for completeness:

- **Timing.** The cold `why taxi` took 8.5 s, because the profile computes exact distinct counts over 20 M rows. The warm call took 0.02 s, from the profile cache. Neither is held to the 100 ms observe budget, which is stated for a small corpus.
- **Plan coverage.** No command panicked or hung, and every `latest` and `asof` plan matched its oracle.

## Verdict

On data it had never seen, the tool's numbers were right everywhere I could check them:

- Every predicted byte count equaled the plan.
- Every exact plan equaled a row-level oracle.
- Every temporal plan held exactly the row groups that hold a wanted version.
- `reconcile` proved a 20-million-row rewrite identical, and caught a single changed `tip_amount` in one row.
- `fix` produced an intact receipt whose prediction the post-apply plan reproduced to the byte.

It also told the truth about the taxi data: no index on pickup zone or vendor can help, because every value is in every row group. In that sense it did its job.

It did not do the whole job:

- **Nested data.** It cannot index any dataset that has a nested column, so raw GH Archive was out of reach until DuckDB flattened it.
- **Explanations.** It reports a negative result as a missing index ("no index serves this lookup") rather than as a layout problem.
- **Temporal savings.** It cannot see the temporal saving that its own `latest` delivers on the same keys.
- **Naming failures.** Its human `reconcile` output does not name the row that failed.
- **No-op fixes.** It will attest a fix worth zero bytes.

The engine is trustworthy. The explanations and the edges are not finished yet.

## Reproduce

```bash
REALDATA_DIR=/path/to/scratch scripts/realdata.sh      # builds release, downloads ~1.2 GB
```

The script needs `curl`, `duckdb`, `jq`, `perl`, and `cargo`. It stops if `/` has less than 8 GB free. It verifies every download against its `Content-Length`. Bytes, row groups, and key choices reproduce exactly. Hashes and wall times do not, because records carry `created_at`.
