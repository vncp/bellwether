# Measured: questions people ask, answered three ways

Every number on this page is a row of [`results/showcase.json`](results/showcase.json), written by [`scripts/showcase.sh`](../../scripts/showcase.sh) and rendered by [`scripts/render_charts.py`](../../scripts/render_charts.py); the tables between the markers below are generated and CI checks that they match the file. Each row names the machine, the build, and the date it was measured on.

## What was measured

Each question is a lookup a person or a job actually runs: the rows for a set of keys, perhaps in a time window; the newest row per key; the row per key current at an instant; and, for market data, the row per symbol valid at one time as known at a later one, so a backtest cannot see the future. Each is answered on the same files three ways:

- **Full scan.** Every row group of the dataset. Bytes are the compressed sizes summed from the Parquet footers.
- **DuckDB alone.** The question as SQL (`SELECT *` with the keys as a literal `IN` list, window functions with `rank() = 1` for newest and as-of), run by the DuckDB command-line tool with its own pruning (min/max statistics, filter pushdown). Bytes and row groups are what DuckDB's JSON profiler reports (`io.total_bytes_read`, `total_row_groups_scanned`); time is the profiler's query time, the median of three warm runs.
- **Bellwether.** `bellwether why` on the unindexed folder (what the question costs today, and what each candidate key would cost, by exact replay), then `bellwether fix` on the key `why` recommended, or on the cheapest candidate when it recommended none, so a key that cannot help is put to `fix` and refused. After `fix`, the lookup verb (`locate`, `latest`, or `asof`) prints its plan, and DuckDB runs the same SQL restricted to the plan's row groups (`file_row_number` ranges, which DuckDB prunes to the row group), measured like DuckDB alone. The two DuckDB answers are fingerprinted (row count and an order-independent hash of every row) and the script stops if they differ; they never did.

Every question gets its own index directory, so no question sees another's key. Reconcile compares two copies of a dataset by key with `bellwether reconcile` (default 256 MiB memory budget), against DuckDB's `EXCEPT ALL` both ways over the same files.

### Datasets

- **NYC taxi**: yellow trips for 2024-01 through 2024-06, the files as published by the city's TLC. The published files carry no min/max statistics for `tpep_pickup_datetime`, so no engine can skip a row group by pickup time from the footers alone; a temporal key records each zone's time bounds per row group when it is built.
- **GH Archive**: the hours 00 to 11 of 2024-01-01, flattened by DuckDB from nested JSON to `repo_id`, `actor_id`, `type`, `created_at` (one file per hour, so `created_at` statistics already separate the hours).
- **ClickBench**: `hits_0.parquet` through `hits_9.parquet` of the `athena_partitioned` split. The rows are sorted by `CounterID`, so DuckDB's statistics already prune a `CounterID` lookup; `UserID` is scattered.
- **Market (synthetic)**: `bellwether bench market --rung medium --seed 7`, prints with restatements and late arrivals. Generated by the binary under test; included because no public dataset has a known-time column.

Keys are distinct values chosen by a seeded hash (`ORDER BY hash(col, 42)`), so a rerun picks the same ones.

### What is not run through `fix`, and why

- **The bitemporal key.** Bitemporal keys (`temporal2:symbol@ts,known_at`) cannot be proposed or receipted yet; that needs a record-format change planned with storage version 2. For the no-lookahead question the key is built with `bellwether index`, so that row has a plan but no prediction and no receipt, and says so. `why` prices the question's valid-time as-of, which is what its "unindexed" row shows.
- **Hive partitioning on the market corpus.** The market folder is read as plain files on every side, not with `--partitioning hive`, because `fix` does not yet record `--partitioning` in the index it builds. The questions never filter on the `day=` directories, so no byte changes; `scripts/showcase.sh --market-hive` reads them as partitions once `fix` records it.

## Reading the numbers honestly

- **Where DuckDB already does well, the index adds nothing.** Sorted data (ClickBench by `CounterID`) and files split by time (GH Archive by hour) let DuckDB's own min/max statistics skip row groups; the table's last column says so wherever DuckDB alone read as little as the plan.
- **Where the keys sit in every row group, nothing helps,** and `fix` refuses (`nothing_to_gain`) rather than attest a key that saves nothing. That is a property of the layout (rows are not clustered by the key), not of a missing index.
- **Bytes are exact; times are not.** Bytes, row groups, and row counts are the same on every run over the same files. Times depend on the machine and on whatever else ran on it; each timed row carries the machine's load average in its `notes`.
- **The plan costs time.** Bellwether's time is the lookup verb's whole process (start, read the index, plan) plus DuckDB on the plan. On small datasets, or where DuckDB prunes as well, that is overhead.
- **How DuckDB reads the plan is not tuned for speed.** It gets the plan as one `read_parquet` per file with `file_row_number` ranges, joined by `UNION ALL`. DuckDB prunes those ranges to the row group (its profiler confirms the row groups and bytes), but the query can run slower than DuckDB's own scan even when it reads fewer bytes (ClickBench, 10 users). Handing the plan to an engine natively is milestone M7.
- **Not measured here:** cold caches, object storage (every file is on local disk), and engines other than DuckDB.
