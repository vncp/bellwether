# ADR 030: Multi-machine build: workers write segments, one committer commits once

**Status:** accepted · **Date:** 2026-10-26

## Decision

An index build can be split across machines that share nothing but the data root (mounted at one path) and the index store. Coordination is through the store only: no service, no lock, no new manifest field, no changed segment byte. Three steps, each an `index` flag:

1. **Plan** (`index <root> --key … --plan-work <dir> [--items N | --item-row-groups M]`), on the committer's machine. It runs everything a single-machine build runs before it reads a row group, with the same code: discovery, fingerprints, validation of the saved row-group space, id assignment (the committer stays the single writer of `rowgroup_space`, ADR 013), each target's work, and the build's own work items (runs of consecutive live ids needing the same targets, cut at file boundaries and at `max_segment_row_groups`). It commits nothing. It writes `work/<run id>/items/<n>.json` for each work item (a run of consecutive build items), then `work/<run id>/plan.json`, to the index store, and a copy of the plan to `<dir>/plan.json`. The run id is the BLAKE3 of the plan's bytes. The plan records its base (sequence, the manifest's content hash, and digests of its row-group space, schema, and source), the row-group space, schema, and source the commit will publish, the targets kept and rebuilt, what workers read (the declared targets, the caps, the excluded directories), each item's hash, and the engine version and Unicode tables. A published plan has all its items (items are written first), and no file under `work/<run id>/` is ever overwritten with other bytes.
2. **Work** (`index --worker <plan.json> --item <n> [--index …]`), on any machine. The worker checks the plan (its exact spelling, its engine version and tables, that this store holds it under its run id) and its item (its hash in the plan), runs the item's build items through the build's own worker path (same caps, same memory bound, the processed row-group range recorded in each segment), uploads each segment content-addressed, fingerprints every file it read after reading it, and writes `work/<run id>/done/<n>.json` with a checksum: segment ids, targets, kinds, ranges, and bytes; the fingerprints; row groups read; tombstone counts; threads and elapsed time. A file that differs from the plan's fingerprint is refused naming the item and the file, and no done file is written. A worker never reads or writes a manifest. Rerunning an item uploads the same bytes and leaves an equal done file in place.
3. **Commit** (`index --commit <plan.json> [--index …]`), once, on the committer's machine. It requires a done file for every item (the refusal names each missing one), refuses a done file that is damaged, re-spelled, another run's or item's, or whose checksum does not match; re-verifies each worker's fingerprints against the plan's (a mismatch names the file and the item to rerun); checks that each item's segments tile exactly its build items' row groups per target (each range starts and ends at row groups of the build item, none overlaps, none is missing, no segment is listed twice); reads every listed segment back (present, its BLAKE3 equal to its id, its size the listed one, its header the listed target's with the listed range); and then runs the build's own commit closure once with the union, in the order a single-machine build commits. If the base's row-group space, schema, or source changed since the plan, it refuses `work plan stale; run --plan-work again`, exactly the single-machine restart rule (the ids the plan assigned may collide). It also refuses as stale a manifest that already references a segment the plan adds (another committer of the plan, or an earlier commit whose answer was lost) or that covers, for a kept target, a live row group the plan indexes (the plan's segments committed and then compacted away), since a rebase onto either would count those row groups twice. A garbage-collection claim on an uploaded segment is retried as a build retries it (with backoff, `max_restarts` times); a segment that collection deleted is refused naming the item to rerun, which re-uploads the same bytes.

The committed manifest equals, byte for byte apart from the fields every commit stamps from the clock or a random source (`committed_at`, `commit_nonce`, `created_at` of a new index, and the `since` of segments it stops referencing and of ids it retires), the manifest a single-machine build of the same work over the same base commits; every lookup plan over it is the same.

## Fault model

- **A lost worker** is a missing done file: the commit names the item; rerun it anywhere.
- **A worker over other data** (a stale copy, a file changed since the plan) refuses itself, naming the item and the file; the committer refuses a done file whose fingerprints differ. Rerun on a machine whose copy matches, or, if the data changed for good, plan again.
- **A crashed worker** leaves uploaded, unreferenced segments: orphans that garbage collection tombstones and, after retention, deletes. The plan is reusable; rerunning the item uploads the same bytes.
- **A lost committer** leaves orphans and a reusable plan: run `--commit` again. If its commit had landed, the second commit reports the plan stale and already committed.
- **Two committers** of one plan are serialized by the manifest's conditional PUT: the loser rebases onto the winner's manifest and sees `stale` (already committed).
- **A concurrent build** (single-machine or another plan) that commits between plan and commit makes the plan stale when it changed the row-group space, schema, or source; uploaded segments become orphans. Compaction and garbage collection in between are rebased onto, as for a single-machine build.
- **Garbage collection** of uploaded segments: a segment uploaded longer ago than the retention window before its commit may be claimed or deleted. A claim is retried; a deletion is refused naming the item to rerun.
- **A damaged or forged plan, item, or done file** is refused before use: a plan by its run id (its path) and exact spelling, an item by the hash its plan records, a done file by its checksum, spelling, run, item, tiling, and the segments' content and headers. These checks catch damage, cross-wired files, stale files from another run, and hand edits; they are not a defense against someone holding write credentials to the store, who could rewrite the manifest directly.
- **Version skew**: a worker or committer of another engine version, or with other Unicode tables, refuses the plan (segment bytes are only the same within one version).

## Rejected alternatives

- **Workers commit their own segments** (one commit per worker, rebasing): every commit after the first sees another worker's ids and segments, the manifest goes through partial states readers can pin (a key incomplete for minutes), and completeness (ADR 012) would be recorded by whichever worker came last. One commit keeps readers on one version (invariant 4).
- **A coordinator service or a lease table**: a second consistency mechanism beside the manifest's conditional PUT, with its own failure modes; the store already serializes the one write that matters.
- **Workers assign their own ids**: ids would collide across workers; the committer is the single writer of `rowgroup_space` (ADR 013).
- **A manifest field for runs in flight**: the frozen format (ADR 028) is not changed for an operational artifact; the work folder is its own format, versioned in its `format` field.
- **Work items with their own segment cuts** (`--item-row-groups` changing `max_segment_row_groups`): the segments would then differ from a single-machine build's. A work item is a run of the build's own items, so the split never changes a byte.

## Consequences

Build crate module `work` (`Builder::plan_work`, `work_item`, `commit_work`; formats `bellwether-work-plan/1`, `bellwether-work-item/1`, `bellwether-work-done/1`); the facade's `Engine::plan_work`, `work_item`, `commit_work`; `index --plan-work`, `--items`, `--item-row-groups`, `--worker`, `--item`, `--commit`. The single-machine build is unchanged in behavior; its attempt was split into a planning phase both paths share and a commit closure both run. No persisted byte of the manifest, segments, or records changes; layering is unchanged. The work folder is never read by readers or garbage collection; after a commit it is an audit trail the operator may delete. Measured: the same-host process proxy in `docs/measured/`, labeled as such; a multi-host number is published only when a second host is used.
