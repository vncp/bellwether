# Threat model for the agent surface

**Claim:** a compromised, confused, or hallucinating agent can waste your time by proposing bad ideas, and can do nothing else.

| Surface | What it can do | Worst case |
|---|---|---|
| `observe.*` (`observe.why` with no keys, `observe.profile`, `observe.locate`, `observe.asof`) | read footers and the index; write the profile Evidence and cache entries | the agent reads evidence |
| `score.*` (`score.why` with keys or a workload, `score.verify`) | ask the engine to replay and verify; the engine writes its own Proposals, Replays, plan Evidence, and Certificates, each computed immediately before it is written; charged to the session budget | the agent spends its budget and is refused with `budget_exceeded` |
| `propose.*` | write a `Proposal` with no score, or nothing with `dry_run` | the ledger holds a bad proposal that scores poorly and never gets a Certificate |
| `apply.receipt` | take a Certificate hash only; the engine applies and then writes the Receipt | the agent asks to apply something unverified and is told no, with a typed code |
| `jobs.*` | start a score or apply call as a job, poll it, read its result | whatever the started tool may do |
| resources (`bellwether://findings`, `receipts`, `scorecard`) | read the ledger | the agent reads the ledger |

`observe.why` and `score.why` are the same facade call (`why`) split by cost. Without keys it reads footers and records the profile Evidence: read-only on the data and cheap. It writes no Replay and reads no rows to verify, so it never spends the replays or rows budget, but like every tool call it is charged its wall time, and it is refused with `budget_exceeded` once any dimension of the session's budget is spent. With keys (a Parquet file) or a recorded workload hash it replays the lookup under every candidate key, which can take minutes and writes engine-scored records, so it sits in the score tier, runs as a job unless the agent asks to wait, and is charged replays as well. `observe.why` has no `keys` field; passing one is `invalid_input`.

Rules that make the claim true:

- No tool accepts a file path to write, a shell command, or a query string to execute. Rewrites are data (`RewriteShape`: before, after, invariant), never code the engine runs. The paths a tool does accept (a key file, a rewrite's before and after output folders) are only read.
- Every tool's input schema is generated from the contract's types (the `schema` feature of `bellwether-types`) and closed: every object, nested ones included, has `additionalProperties: false`. A `score`, `confidence`, or `replay` field anywhere in a propose call is `invalid_input`, and nothing is written.
- The engine never calls the model. The model calls the engine. The direction of dependency is the security property.
- `apply.receipt` resolves the Certificate and refuses unless `pass == true` and the certificate was computed against the current manifest version, and unless the files are those the certificate verified. A key that is already complete is refused (`nothing_to_apply`) before the proposal is re-scored, so the dry run and the real apply give the same answer and the refusal writes nothing. Only after the apply succeeds does the engine write the Receipt, recording `manifest_before` (the version the certificate was computed against) and `manifest_after` (the version the apply produced). A hash that names another kind of record is refused as `wrong_kind`. The one refusal that follows writes is `concurrent_commit`: another commit landed during the apply, so the key is built but the receipt is withheld.
- `Proposal` has no score field. Scoring cannot be injected because there is nowhere to put it. The proposer name `engine` is reserved (`reserved_proposer`).
- Every refusal carries a stable `code`, the facts needed to act (the mismatch counts and first mismatching keys of a failed certificate, the untracked, changed, and missing files of a stale index, the argument to fix), and one `next` line naming MCP tools and fields, never a CLI flag. `AGENTS.md` lists every code; the test suite fails if a code is missing from it.
- `dry_run: true` on `propose.*` and `apply.receipt` runs every check and returns what would be written or refused, and writes nothing anywhere (tests compare the whole temporary tree's object list before and after, with and without a fixed clock, and an index location that does not exist yet stays absent).
- Each server process is one session with a budget (`--budget-replays`, `--budget-rows`, `--budget-seconds`): Replay records written, rows the verifier read, and wall time of every tool call. A spent dimension refuses every further call, of any tier, with `budget_exceeded` before it runs. A score or apply call is admitted atomically: under the budget lock it is checked and reserves the replays and rows left, and a concurrent one waits until that reservation settles (its actual cost charged, the rest refunded) and is then checked. The facade's operations are not cancellable, so the call that crosses a limit finishes over it, and it is the only one.
- A job id names one run and one result: it hashes the request and the state the result depends on (the manifest sequence and the data's catalog digest), so starting or calling the same request again in the same state returns that job, and its stored result once finished, while a retry after a commit or a data change (as the `stale_manifest` and `data_changed` next lines ask) is a new run.
- Every result's envelope lists the record hashes it rests on (`cites`) and, for every receipt it mentions, the receipt's explain chain and whether it is intact.
- Every Evidence and Certificate carries provenance: inputs, age, creation time, and the manifest version when one exists (always for a Certificate; an Evidence about an unindexed folder has none yet). An agent cannot present stale numbers as fresh; the age is on the record.
- The server reads nothing from the environment (except the variable a table root's `db=env:NAME` names, which the human chose when starting it), logs to stderr only, and opens no network connection beyond the store the facade opens and the database a table root names.
- A data root may be a table (`sql://...`, ADR 027), named by the human when the server starts, never by a tool argument. Over it the engine runs only SQL it writes itself: a catalog listing, one aggregate query per unit, an ordered scan of a range column, a projected `SELECT` per unit, and `BEGIN`/`ROLLBACK` around the run (read-only where the engine has read-only transactions; SQLite is opened read-only). Identifiers are quoted and every literal is a value the engine itself returned. A rewrite's text is never executed: over a table, `fix` and `apply.receipt` verify and then refuse with `attest_only`, naming the statements for a human. The connection string never reaches a record or a result; records name `sql://<engine>/<tables>` only. The crate's `MeasuredScorer`, which does run SQL text, is not reachable from any tool.

Tests: `crates/bellwether-mcp/tests/threat_model.rs` (the loop end to end, smuggled scores, every apply refusal writing nothing, refusal facts, budgets, jobs; each write-nothing test under a fixed clock and the system clock), `review_probes.rs` (concurrent jobs against the budget, the rows and seconds limits, every loop refusal typed with its MCP field, dry runs against an absent index location, the apply dry run and the apply agreeing on a built key, a finished job returned not rerun), `proptest_inputs.rs` (arbitrary and mutated JSON on every tool never panics and never writes outside the tool's tier), `catalog.rs` (closed schemas, the prompt is `AGENTS.md`), `stdio.rs` (the binary over a real stdio session), and `crates/bellwether-cli/tests/mcp.rs` (ADR 010: every tool's text is the CLI's `--json` line, with default and non-default arguments).

Out of scope: an attacker with write access to the store. Content addressing makes tampering detectable but not preventable; signing is a later addition.
