# Threat model for the agent surface

**Claim:** a compromised, confused, or hallucinating agent can waste your time by proposing bad ideas, and can do nothing else.

| Surface | What it can do | Worst case |
|---|---|---|
| `observe.*` (`observe.why` with no keys, `observe.cardinality`, `observe.overlap`, `observe.profile`, `observe.locate`, `observe.asof`, `observe.text`) | read footers and the index; write the profile Evidence and cache entries | the agent reads evidence |
| `score.*` (`score.why` with keys, a workload, or text lookups, `score.verify`, `score.record`) | ask the engine to replay and verify; the engine writes its own Proposals, Replays, plan Evidence, and Certificates, each computed immediately before it is written; charged to the session budget | the agent spends its budget and is refused with `budget_exceeded` |
| `propose.*` | write a `Proposal` with no score, or nothing with `dry_run` | the ledger holds a bad proposal that scores poorly and never gets a Certificate |
| `apply.receipt` | take a Certificate hash only; the engine applies and then writes the Receipt | the agent asks to apply something unverified and is told no, with a typed code |
| `jobs.*` | start a score or apply call as a job, poll it, read its result | whatever the started tool may do |
| resources (`bellwether://findings`, `receipts`, `scorecard`) | read the ledger | the agent reads the ledger |
| signing: `bellwether fix --signing-key` (attest) and `fix --verify-only --signing-key` (verify); the server's `--signing-key` for `apply.receipt` and `score.verify` | sign, with a key read from a path the operator gives, only the Receipt and the Certificate the same call wrote, right after the ledger accepted them; no tool takes a key, a hash to sign, or a signature | nothing: an agent cannot choose what is signed, and every other tool signs nothing |

`observe.why` and `score.why` are the same facade call (`why`) split by cost. Without keys it reads footers and records the profile Evidence: read-only on the data and cheap. It writes no Replay and reads no rows to verify, so it never spends the replays or rows budget, but like every tool call it is charged its wall time, and it is refused with `budget_exceeded` once any dimension of the session's budget is spent. With keys (a Parquet file) or a recorded workload hash it replays the lookup under every candidate key, which can take minutes and writes engine-scored records, so it sits in the score tier, runs as a job unless the agent asks to wait, and is charged replays as well. `observe.why` has no `keys` field; passing one is `invalid_input`.

Rules that make the claim true:

- No tool accepts a file path to write or a shell command. Rewrites are data (`RewriteShape`: before, after, invariant), never code the engine runs on the lake. The paths a tool does accept (a key file, a rewrite's before and after output folders) are only read. The one exception for query text is a query engine the human named at startup (`--twin-of`, ADR 033): a rewrite's `pairs` (in `score.verify` and `apply.receipt`) and `score.record`'s keys query are submitted to that engine only, under the engine's own read-only setting (ClickHouse `readonly=2`, Kusto `request_readonly`; a Kusto text starting with `.` is a management command and is refused), each under a tag bellwether chose, and their rows are discarded or exported into the human's `--scratch` folder. No tool argument names an engine, a connection, a credential, or a scratch folder.
- Every tool's input schema is generated from the contract's types (the `schema` feature of `bellwether-types`) and closed: every object, nested ones included, has `additionalProperties: false`. A `score`, `cost`, `replay`, `stats`, `measured`, `prediction`, `verdict`, or `certificate` field (the list is `bellwether_mcp::refusal::COST_FIELDS`) anywhere a tool does not take it is `caller_supplied_cost`, any other unknown field `invalid_input`, and nothing is written. There is no import of an engine's query statistics: the engine reads them itself, by its own tags.
- The engine never calls the model. The model calls the engine. The direction of dependency is the security property.
- `apply.receipt` resolves the Certificate and refuses unless `pass == true` and the certificate was computed against the current manifest version, and unless the files are those the certificate verified. A key that is already complete is refused (`nothing_to_apply`) before the proposal is re-scored, so the dry run and the real apply give the same answer and the refusal writes nothing. Only after the apply succeeds does the engine write the Receipt, recording `manifest_before` (the version the certificate was computed against) and `manifest_after` (the version the apply produced). A hash that names another kind of record is refused as `wrong_kind`. The one refusal that follows writes is `concurrent_commit`: another commit landed during the apply, so the key is built but the receipt is withheld.
- `Proposal` has no score field. Scoring cannot be injected because there is nowhere to put it. The proposer name `engine` is reserved (`reserved_proposer`).
- Every refusal carries a stable `code`, the facts needed to act (the mismatch counts and first mismatching keys of a failed certificate, the untracked, changed, and missing files of a stale index, the argument to fix), and one `next` line naming MCP tools and fields, never a CLI flag. `AGENTS.md` lists every code; the test suite fails if a code is missing from it.
- `dry_run: true` on `propose.*` and `apply.receipt` runs every check and returns what would be written or refused, and writes nothing anywhere (tests compare the whole temporary tree's object list before and after, with and without a fixed clock, and an index location that does not exist yet stays absent).
- Each server process is one session with a budget (`--budget-replays`, `--budget-rows`, `--budget-seconds`): Replay records written, rows the verifier read, and wall time of every tool call. A spent dimension refuses every further call, of any tier, with `budget_exceeded` before it runs. A score or apply call is admitted atomically: under the budget lock it is checked and reserves the replays and rows left, and a concurrent one waits until that reservation settles (its actual cost charged, the rest refunded) and is then checked. The facade's operations are not cancellable, so the call that crosses a limit finishes over it, and it is the only one.
- A job id names one run and one result: it hashes the request and the state the result depends on (the manifest sequence and the data's catalog digest), so starting or calling the same request again in the same state returns that job, and its stored result once finished, while a retry after a commit or a data change (as the `stale_manifest` and `data_changed` next lines ask) is a new run.
- Every result's envelope lists the record hashes it rests on (`cites`) and, for every receipt it mentions, the receipt's explain chain and whether it is intact, the signatures beside the receipt and its certificate, and, when the server was given `--trusted-keys`, the chain's verdict (`signed`, `untrusted`, `unsigned`, or `invalid`).
- Every Evidence and Certificate carries provenance: inputs, age, creation time, and the manifest version when one exists (always for a Certificate; an Evidence about an unindexed folder has none yet). An agent cannot present stale numbers as fresh; the age is on the record.
- The server reads nothing from the environment, logs to stderr only, and opens no network connection beyond the store the facade opens, the database a table root names, and the query engine `--twin-of` names (its table listing for `why`, the tagged queries, log reads, and exports for `score.*`); it reads from the environment only the variable a table root's `db=env:NAME` names, chosen by the human at startup. Its signing key and trust file are paths given as flags at startup, read once.
- A data root may be a table (`sql://...`, ADR 027), named by the human when the server starts, never by a tool argument. Over it the engine runs only SQL it writes itself: a catalog listing, one aggregate query per unit, an ordered scan of a range column, a projected `SELECT` per unit, and `BEGIN`/`ROLLBACK` around the run (read-only where the engine has read-only transactions; SQLite is opened read-only). Identifiers are quoted and every literal is a value the engine itself returned. A rewrite's text is never executed: over a table, `fix` and `apply.receipt` verify and then refuse with `attest_only`, naming the statements for a human. The connection string never reaches a record or a result; records name `sql://<engine>/<tables>` only. The crate's `MeasuredScorer`, which does run SQL text, is not reachable from any tool.

Tests: `crates/bellwether-mcp/tests/threat_model.rs` (the loop end to end, smuggled scores, every apply refusal writing nothing, refusal facts, budgets, jobs; each write-nothing test under a fixed clock and the system clock), `review_probes.rs` (concurrent jobs against the budget, the rows and seconds limits, every loop refusal typed with its MCP field, dry runs against an absent index location, the apply dry run and the apply agreeing on a built key, a finished job returned not rerun), `proptest_inputs.rs` (arbitrary and mutated JSON on every tool never panics and never writes outside the tool's tier; without `--signing-key` no tool writes a signature, with one only `apply.receipt` and `score.verify` do, and over the loop they sign exactly the records they wrote), `catalog.rs` (closed schemas, the prompt is `AGENTS.md`), `stdio.rs` (the binary over a real stdio session), and `crates/bellwether-cli/tests/mcp.rs` (ADR 010: every tool's text is the CLI's `--json` line, with default and non-default arguments). Signing itself: `crates/bellwether-ledger/tests/signatures.rs` (every verdict and refusal, a moved, re-kinded, re-dated, or bit-flipped signature, an every-byte corruption sweep), `crates/bellwether/tests/signing.rs` (byte-identical signatures under a fixed clock, nothing but `fix` signs, the key never in the store), and `crates/bellwether-cli/tests/keys.rs` (keys round trip, a key file others can read refused before anything is scored, the `--require-signature` gate).

Out of scope, and what signing changes (ADR 029): an attacker with write access to the store can still plant or alter records, and content addressing detects alteration. With signing, a planted receipt, certificate, or chain carries no signature from a trusted key, and a gate that requires one (`receipt show --require-signature`, WP17's CI gate) refuses it. The gate requires all of: every link of the chain present and readable (a deleted or altered link is named); the receipt and its certificate each signed by a key in the reader's trust file, within the key's validity window; and the chain's evidence about this data root. Signatures bind content, not location: a signed chain copied from an index of another data root path is still validly signed, so the gate refuses it by its evidence's root ("signed, but for <root>"). The check compares the canonical data-root path, not the dataset: a chain signed over a different dataset that lived at the same path (moved away, another machine, another CI checkout) is not told apart. The signing key never enters the store (it is read from a path, never from an argument or the environment's bytes, and only its public half is written beside a record; a key or trust file inside the index location is refused, exit 2), the engine signs only records it wrote in the same call, and a signature binds kind, hash, and time (`bellwether-signature-v1\0 ‖ kind ‖ 0x00 ‖ hash ‖ signed_at`), so it cannot be moved to another record, kind, or time. The trust file belongs to the reader and is never stored in the ledger, so an attacker who can write the store cannot also choose who is trusted. Text read from the store (signature objects, record fields, unreadable-record reasons) reaches a terminal or an agent with control characters escaped, so a planted object cannot forge output lines. What signing does not do: it does not make a bad certificate good (the ledger rules still decide what a receipt may cite, and `sign` re-runs them before signing); it does not protect against a compromised signer host, which holds the key; and a validity window retires an honest key only. `signed_at` is what the signer asserts, so a stolen key can sign with a time inside its window: a compromised key must be removed from the trust file, not given a `revoked_at`.

Query engines (ADR 033). The engine a lake is a twin of is named by the human (`--twin-of`), with secrets only as `password=env:NAME` or the Azure Identity credential chain; records name the root without user or parameters. `observe.why` with a twin reads only the engine's table listing (ClickHouse `system.parts`, Kusto `.show extents`) for its identity. The only query text an agent hands over is `score.record`'s keys query and a rewrite's pairs; the engine submits it under its own tags to that one engine, never to the lake or a shell, read-only where the engine has the setting (ClickHouse `readonly=2` for the query and its export; Kusto `request_readonly` for the query, while its export is the `.export` management command with the query as its source, so the principal's rights in that database bound what it can do). Every cost of an engine rewrite comes from the engine's own query log, read by tags bellwether chose, never from a caller; there is no `measure import` command and no field to carry one, and a cost-like field in any tool's arguments is refused by name (`caller_supplied_cost`). Exports land in the human's scratch folder (under the lake's own account and permissions), are deleted after the certificate unless `--keep`, and only their hashes and counts reach a record. A refused export is `export_denied`: no certificate, no receipt. An engine receipt is attest-only (`attest_only: true`, `manifest_before == manifest_after`): bellwether creates nothing inside the engine. Tests: `crates/bellwether/tests/engine_twin.rs` (the loop with an in-process adapter, export denial, a fabricated replay, the prediction on a failing certificate), `crates/bellwether-mcp/tests/engine_tools.rs` (the tools against the facade's JSON line, `caller_supplied_cost` direct and as a job), `crates/bellwether-cli/tests/engine_tools.rs` (CLI and MCP byte identity against ClickHouse, CI), `crates/bellwether-source-engine/tests/clickhouse.rs` (the reference adapter against a server, CI).

What the agent's text can still do inside the engine (ADR 033 amendment). The text runs with every read privilege of the connecting user, network table functions included (ClickHouse `url()` works under `readonly=2`), so the connecting user should have least privilege: `SELECT` on the twin's tables and on the query log, nothing else, network table functions revoked. The text can tell its runs apart, by its own query id, the `bw-` prefix of the tag, or its output format; it gains nothing from that, because each query runs once, the run whose rows are exported is the run whose statistics are read, the rows the log says it returned must be the rows it exported (`measurement_refused`, `result_rows_differ`), and the apply tier's own run must agree with the certified replay (`measurement_changed`). The text can turn an engine cache on (a `SETTINGS` clause overrides the request's settings): a ClickHouse run that turned the query cache on, or that the query cache or query condition cache served, is refused (`cache_served`), and a Kusto entry missing a scan or cache statistic is refused (`statistics_missing`). A log entry another client wrote under bellwether's tag (another text or user, or a second finished entry) is refused. Exports land only in a hidden folder under the lake root, checked on its canonical path, created with the lake root's permissions.

Round 2 (ADR 033 amendment): ClickHouse runs the agent's text with `readonly=1`, so the text can change no setting at all (no cache, no logging setting, no `SETTINGS` clause), and a log entry that is not fully logged (empty profile events, or settings without the request's `readonly=1`) is refused as `statistics_missing`, so a run that hid its counters can never read as "no cache". Tests: `tests/clickhouse.rs::a_query_text_that_changes_a_setting_or_an_entry_not_fully_logged_is_refused` (the review's variants, and the same text run by another route), `::a_user_whose_queries_are_not_fully_logged_is_refused`, and the CLI probes test.

Least privilege on ClickHouse: the connecting user should hold `SELECT` grants and no `readonly` in its profile. Bellwether sets read-only mode on every request itself (`readonly=1` for the agent's text); a profile that sets `readonly` refuses any request that chooses its own, so the adapter refuses at connect and names the user's profile (`tests/clickhouse.rs::a_user_whose_profile_sets_readonly_is_named_at_connect`).
